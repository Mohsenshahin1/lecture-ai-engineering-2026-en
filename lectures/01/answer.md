## Exercises

- Differences between the Lecture 01 (bare LLM) and agent answers: In Lecture 01, `app.ask` (the bare model, no tools) was asked a course-specific question ("What are the 3 homework levels...") and explicitly said it had no access to that information. Here, `app.agent` was asked a different but equally course-specific question ("What is a lecNN-start tag?") and answered it correctly and confidently, explaining that it is a Git tag marking each lecture's starting code (e.g. `lec03-start`) and even noted its purpose (letting students start a lecture's exercises from a clean point even if the previous one isn't finished). The same underlying model (gemini-3.5-flash-lite) went from "I don't know" to a correct, grounded answer purely because it now has a `search_glossary` tool and INSTRUCTIONS telling it to use that tool before answering course-specific questions — a direct demonstration of "agent = model + harness".
- Tool calls shown by `--trace` (tool names and arguments): For "What is the difference between LoRA and QLoRA?": `search_glossary({'query': 'LoRA'})` then `search_glossary({'query': 'QLoRA'})`, i.e. two separate single-term searches rather than one combined search, matching the docstring's instruction "Put only one term to look up in query". For "Give me one review question from Lecture 02" (after adding make_quiz): `make_quiz({'lecture': 2})`, which returned a JSON question/answer pair that the model then rephrased into a natural-language review question, also appending a thinking hint before the answer.
- Number of LLM calls for one question (`requests`): The LoRA/QLoRA question used `requests=2, tool_calls=2` (two searches, two corresponding model calls). The make_quiz question used `requests=2, tool_calls=1` (one tool call, but two LLM round-trips: one to decide to call the tool, one to compose the final answer from its result).
- Tool added and the description in its docstring: Added `make_quiz(lecture: int)` to `app/tools.py`, which picks a random glossary term from the given lecture and returns a `{"question": ..., "answer": ...}` JSON pair. Docstring: "Pick one term from the given lecture and return a review question and its answer. Use when asked for review questions, such as 'Give me a review question for Lecture 2'." Registered in `app/agent.py` with `agent.tool_plain(tools.make_quiz)`. Initially hit a `NameError: name 'random' is not defined` because `import random` was missing from the top of `app/tools.py`; adding the import fixed it, and `uv run pytest -q` then passed all 11 existing tests, confirming nothing else broke.

## Homework

- Level attempted: Basic
- What you did: Ran a 3-step controlled experiment on the same question ("What is the difference between LoRA and QLoRA?") with `--trace`. Step 1 (baseline): unmodified `INSTRUCTIONS` and docstrings. Step 2: removed the line "Always check the glossary with search_glossary before answering about terms or course-specific information." from `INSTRUCTIONS` in `app/agent.py`. Step 3: additionally removed "Use before answering about AI engineering terms or words specific to this course (AIE2026)." from `search_glossary`'s docstring in `app/tools.py`, leaving only its core description and the "one term per query" rule.
- Results: Tool-calling behavior was identical across all three runs: `search_glossary({'query': 'LoRA'})` then `search_glossary({'query': 'QLoRA'})`, with `requests=2, tool_calls=2` every time. The one consistent, monotonic change was input token count, which dropped with each removal (1277 → 1235 → 1191), confirming the edits took effect. Output tokens fluctuated slightly (209 → 248 → 219) without a clear trend, likely normal generation variance. All three answers correctly cited "Lecture 02" (or "(Lecture 02)" in the final run) and remained accurate and well-grounded in the real glossary definitions throughout.
- Observations and questions: I expected removing the explicit "always search" instructions (at both the agent level and the tool level) to eventually stop the model from calling search_glossary, but it never did across either removal. One remaining INSTRUCTIONS line I deliberately kept, "End your answer by indicating the relevant session (Lecture NN)", likely still forces a search indirectly, since the lecture number for a term is only available from the glossary's `lecture` field and cannot be reliably known otherwise. This suggests tool use here is driven less by a single "must-search" command and more by the model inferring it needs information (the correct lecture number) that only a tool can provide, combined with the tool's own name and core description already making its relevance to a terminology question fairly obvious even without an explicit "always use this" instruction. A natural next test (not performed here) would be removing that final citation requirement too, to see whether that is really the deciding factor, or whether the model would still search purely because an obviously relevant, well-named tool was available for a question about defined technical terms.
